# 简历与面试素材

> 这份文档只做一件事：把项目里已经发生的工程决策和实测数字，整理成可以直接用于简历和在面试里展开讲的材料。所有数字都能在仓库里找到出处（见文末索引）。

## 1. 一句话定位

- **简历标题行**：LocalMind · 本地优先的个人知识代理（FastAPI + Qdrant + 双轨 LLM + 长期记忆）
- **自我介绍一句**：做了一个本地优先的 RAG 个人知识代理，索引留在本机、只把命中的片段发给云端，可以随时切到完全离线的本地模型，并能跨会话记住用户说过的事实。
- **技术面试一句**：重点是三件事——检索质量用 40 题评测集量化并驱动参数、云端/本地双轨的可切换抽象与出站控制、以及 SQLite + 向量库的分工与迁移。

## 2. 简历项目描述

### 版本 A（投递用，三条）

- **LocalMind · 本地优先的个人知识代理**（Python / FastAPI / Qdrant / React / DeepSeek + Ollama）
  - 设计混合检索链路：bge-m3 稠密 + jieba/BM25 稀疏、应用层 RRF 融合、bge-reranker 精排，在自建 40 题评测集上 Recall@5 **87.2%**，并用阈值扫参把拒答设计成"检索闸门 + 生成层"两层结构（无答案题 10/10 拒答、有答案题 0 误拒）。
  - 抽象 `ChatProvider` 协议实现云端/本地双轨切换：云端只出站命中的 top-k 片段并给出逐轮出站回执（片段/文件/字符/记忆），本地轨道经抓包验证**零外部连接**；重排按轨道分配 GPU/CPU 以避让显存。
  - 实现长期记忆：每轮答后异步抽取事实/偏好、按稳定 key 覆盖并保留历史、事件时间与记录时间分离，跨会话召回在 5 个场景中 5/5 通过；工程上用 Alembic 幂等基线把无版本表的旧库无损接入迁移体系。

### 版本 B（项目经历栏，六条，可裁剪）

1. **检索与评测**：三路对比（纯向量 / 混合 / 混合+重排）显示 Recall@5 从 82.8% → 91.1% → 87.2%，据此定位"重排对语义改写类问题给分过低"的问题，最终采用两层拒答而不是单一阈值。
2. **双轨抽象**：`ChatProvider` 只约定 `stream_chat`，DeepSeek 与 Ollama 各实现一份；轨道按"请求 > 会话 > 环境默认"解析，切换不重启进程。
3. **出站控制**：服务端执行每轮「仅检索」开关与按资料源黑名单（引用编号重排），每条回答附出站回执；本地轨道用 TCP 采样证明只连环回。
4. **长期记忆**：SQLite 是事实来源、Qdrant 只存活跃向量；key 唯一、覆盖留痕；摘要边界用条件更新抢占，修掉了"同一边界生成两次"的竞态。
5. **多格式与引用定位**：PDF 按页解析、每页独立分块，引用精确到"第 N 页 · 第 K 块"；docx 标题转层级；代码按顶层符号切节。
6. **工程化**：Alembic 迁移（幂等基线 + 前向 revision）、结构化 JSON 日志与逐消息埋点、`docker compose` 三容器一键启动、GitHub Actions（ruff / mypy / pytest / 前端构建）、115 个测试。

## 3. 面试故事线（5 分钟版）

### 3.1 为什么做这个

"我想要一个能问我自己的笔记、并且能说清楚依据来自哪里的工具。市面上的方案要么把整份文档传上去（我不接受），要么只知道通用知识（对个人资料没用）。所以做成本地索引 + 只出站片段，再给一个完全离线的本地轨道兜底。"

### 3.2 三个关键取舍（每个都要能展开）

**取舍一：为什么是"向量 + 关键词 + 重排"三件套，而不是只做向量？**
评测集里 `paraphrase` 类问题暴露了问题：稠密检索召回好但排序差，关键词检索对专有名词准。三路对比数据是 82.8% / 91.1% / 87.2%，看起来"混合最好、重排反而降"，但分开看不难发现重排把 paraphrase 类问题压得太低（同义改写的字面相似度低）。所以最终保留重排（cross_doc 类明显变好），同时把拒答做成两层：闸门阈值只拦"完全无关"，语义改写交给生成层判断。

**取舍二：为什么拒答要分两层？**
单阈值在评测里平衡不了：闸门调高会误拒 paraphrase（top1 重排分 0.001 量级），调低会放过不相关问题。分层之后，第一层不调用云端（省钱、零出站），第二层让模型按 prompt 判断"话题相关但缺事实"——10 道无答案题里，5 道被闸门拦下、5 道被模型拒答，0 误答。

**取舍三：双轨怎么做到"随时可切、不锁死"？**
Provider 协议只要求流式返回文本，不暴露任何厂商细节；轨道解析是三级优先级（请求 > 会话 > 环境默认），会话内切换立即生效。真正难的不是抽象，而是**出站边界**：只有云端路径会经过出站策略，本地路径根本不进那段代码——所以"本地零出站"是结构保证，不是配置正确。

### 3.3 两个踩坑故事

**故事一：同一个属性被抽出两条互相矛盾的记忆。**
现象：先说"用 Python"，两周后说"改用 Go"，模型回答"你之前提到过两种说法，彼此有冲突"。
排查：查库发现同一个 key「技术栈偏好」有两条 active，`kind` 一次是 `preference`、一次是 `fact`。第一版覆盖条件是 `(kind, key)`，kind 漂移就分叉了。
修复：key 成为唯一身份（覆盖与轮内去重都只看 key），并把已有 key 连同标签回喂给抽取器让它沿用。补了回归单测。

**故事二：同一个摘要边界写了两次。**
现象：一个 6 轮会话里出现了两条同 key 摘要。
原因：摘下一条消息的后台任务与当前任务重叠，两者都读到 `count=6`，`count % 6 == 0` 这种判断天然会重复。
修复：把"已摘要到第几条用户消息"落库，用 `UPDATE ... WHERE summarized_user_messages = last` 抢占，抢不到就跳过；失败（超时/向量写失败）时把边界还回去，下一轮重试。同一会话再加一把 `asyncio.Lock` 串行化。

**（可以加的第三个）本地模型的拒答措辞漂移。** 4B 模型把「资料中未找到足够依据」说成「资料中未找到关于…的具体步骤」，功能其实是拒答，但标记匹配不上，前端不显示"资料不足"、评测也算误答。改成匹配更短前缀，并加单测保证"标记出现在句中不算拒答"。

### 3.4 如果重做

- 记忆召回应该按 key 精确查找 + 向量召回两条路并存；现在一句话问两件事时只能召回一件（实测 0.54 分那条）。
- PDF 的"每页强制分块"是拿分块连贯性换引用精度；如果有 OCR 与版面分析，应该按版面区块而不是按页。
- 评测应该把"引用是否逐句支撑"也做掉（NLI 或人工标注），现在只能度量"引用是否指向能回答问题的片段"。

## 4. 高频追问与答案要点

| 追问 | 要点 |
| --- | --- |
| 为什么用 Qdrant，不用 Chroma/FAISS/pgvector？ | 需要命名向量（稠密 + 稀疏并存）、服务端 IDF、payload 过滤；FAISS 是库不是服务、Chroma 稀疏支持弱、pgvector 要多维护一个 Postgres |
| 为什么 SQLite 和向量库要分开？ | 事务、约束、可查询的历史（被覆盖的记忆）；向量库只负责相似度。先写库、后写向量，写失败标 `embedding_ok=false` 而不是丢数据 |
| 嵌入为什么用 Ollama 而不是 sentence-transformers？ | 嵌入始终本机；Ollama 已经常驻，避免再加载一份 2 GB 的模型；重排仍用 sentence-transformers（需要 cross-encoder） |
| 怎么证明"本地模式真的没联网"？ | `scripts/verify_offline.py`：断言出站回执 `enabled=false`，同时在请求期间采样后端进程的 TCP 连接，要求全部是环回地址 |
| 出站策略会不会误伤？ | 被黑名单拦下的片段会在回执里单独计数；如果全部命中都被拦，会明确说"内容被策略拦下"而不是"资料里没有" |
| 引用精确率 85%～89% 怎么来的？ | gold + acceptable 逐字引文标注，按编号匹配；损失主要来自模型过度引用（窄问题也给 3～5 条） |
| 迁移为什么不用 stamp？ | 旧库没有版本表，按 schema 特征猜版本会静默漏列；改成"缺什么补什么"的幂等基线，对任何历史库都成立 |
| 为什么要容器化，反正自己用？ | 为了"面试官/朋友能一条命令跑起来"，也是检验依赖是否真的声明完整；性能路径仍是宿主机 venv |
| 并发怎么处理？ | 每会话一把 `asyncio.Lock` 串行化记忆任务；摘要边界用条件更新抢占；后台任务由 `TaskRunner` 持有，关闭时取消 |
| 最大的技术债是什么？ | 记忆只做语义召回（无精确查找/过期）；评测样本只有 40 题，引用精确率的单次波动 ±3pp；容器路径的 CPU 重排拖慢首 token |
