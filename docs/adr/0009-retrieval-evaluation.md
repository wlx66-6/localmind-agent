# 0009 · 检索与拒答的评测方法

- **状态**：已接受（阶段 2，2026-10-25）
- **日期**：2026-10-25
- **决策者**：项目作者 + 协作代理

## 背景

“检索更准了”“拒答更可靠了”必须能被量化，否则无法比较纯向量、混合召回、混合 + rerank 三种策略，也无法向面试官说明参数为什么这样定。约束：

- 语料是中文个人笔记，规模小（10 篇 / 47 chunk），没有现成中文检索评测集。
- 需要可重复执行、不依赖人工逐题打分。
- 引用判定不用模型裁判（作者已确认），避免“用模型评模型”的循环论证。

## 评测集设计

`eval/stage2/questions.jsonl`，40 题，四类各 10 题：

| 类别 | 目的 | gold |
| --- | --- | --- |
| `exact` | 精确术语 / 数字，验证 BM25 路 | 1 个片段 |
| `paraphrase` | 用词与原文不同，验证 dense 路 | 1 个片段 |
| `cross_doc` | 需要 2～3 个片段综合，验证召回覆盖面 | 2～3 个片段 |
| `unanswerable` | 语料中确实没有答案，验证拒答 | 空 |

**gold 存“逐字引文 + 文件 + 标题路径”，不存 chunk id。** 分块参数变化后仍可评测：运行时用同一个 `chunk_text` 重新切分语料，把引文解析成 `(path, heading, start_line, end_line)`。解析要求恰好命中 1 个 chunk，否则脚本以退出码 2 失败——评测集失效要显式报错，而不是静默降级。

每题另有可选的 `acceptable` 列表：除 gold 之外、同样能支撑正确答案的片段。它只参与引用精确率判定，不参与 Hit/Recall/MRR 计算（检索指标始终以 gold 为准，避免扩充标注改变分母）。标注规则是“该片段是否含有能回答该问题的陈述”：对多部分问题，把同一答案链上的其他支撑段落补进来；只是话题相关、但没有回答问题的片段不纳入。标注以语料原文为准，逐条回读判断，不因为模型引用过就自动接受——实际情况是模型额外引用的片段多数被判定为“仅话题相关”。

16 道有答案题带 `acceptable`（其余 14 道 gold 已足够），共 29 条额外片段。

## 指标定义

| 指标 | 定义 |
| --- | --- |
| Hit@5 | 有答案题中，至少 1 个 gold chunk 进入前 5 的比例 |
| Recall@5 | 有答案题中，前 5 命中的 gold chunk 数 / 该题 gold 总数（宏平均） |
| MRR@5 | 第一个 gold chunk 排名倒数的平均；衡量 top-1 质量 |
| 闸门拒答率 | 无答案题中，top1 分数低于闸门阈值的比例（不调用生成） |
| 误拒率 | 有答案题中，被闸门拦下的比例 |
| 端到端拒答 | 无答案题中，闸门拒答 + 生成层拒答的总比例 |
| 引用精确率 | 回答引用的片段中属于 gold ∪ acceptable 的比例（宏平均：每题先算比例再平均；微平均：按引用条数加权） |
| 引用精确率（严格） | 只认 gold 的比例；同一条回答上另算，作为保守下界 |
| 引用召回率 | gold 片段中被引用的比例（不因 acceptable 放宽） |
| 首 token / 总耗时 | 从请求发出到第一个增量 / 到流结束 |

无答案题不计算 Hit/Recall；引用指标只统计“有答案且实际生成”的题。

## 实测结果（2026-10-25）

环境：RTX 5060 Laptop 8GB / Win11；`bge-m3`（Ollama）+ jieba BM25 + `BAAI/bge-reranker-v2-m3`（CUDA fp32）；集合 `localmind_chunks_v2`，47 点。

| 模式 | Hit@5 | Recall@5 | MRR@5 | 总耗时 p50 |
| --- | --- | --- | --- | --- |
| 纯向量 | 93.3% | 82.8% | 0.776 | 19 ms |
| 混合（RRF） | **96.7%** | **91.1%** | 0.806 | 22 ms |
| 混合 + rerank | 93.3% | 87.2% | **0.844** | 312 ms（rerank 287 ms） |

端到端（hybrid_rerank + DeepSeek，35 次云端调用，2026-10-25 最终一轮）：

- 无答案题 **10/10 拒答**（闸门 5 + 生成层 5），有答案题 **0 误拒**、无答案题 **0 误答**。
- 引用召回 93.3%；引用精确率（gold ∪ acceptable）**89.2%**（宏）/ 84.3%（微）；只认 gold 的严格精确率 65.3%（宏）/ 50.0%（微）。
- 首 token p50 899 ms / p95 1168 ms；总耗时 p50 1.49 s / p95 2.39 s。

## 关键发现 1：rerank 有“字面偏好”，单阈值不能同时保召回和拒答

同一段正确片段，换一种问法，rerank 分数会从 0.8 掉到 0.001：

| 问题 | 分数 |
| --- | --- |
| `稠密检索擅长处理什么？` | 0.999 |
| `向量检索能解决同义词问题吗？` | 0.826 |
| `用户提问的用词和原文不一样时，靠什么方法还能找到相关内容？` | **0.001** |

这解释了为什么单阈值扫参的最优点（0.25）会误拒 3/30 有答案题，而阈值降到 0.01 又只能拦下 5/10 无答案题。分数分布如下：

- 有答案题 top1 最低 0.017（q29）、0.034（q25）、0.077（q12）；
- 无答案题 8 题 ≤ 0.098，但 2 题（q33 `bge-m3 训练数据多少条`、q37 `LoRA 微调显存`）因为话题相关拿到 0.95。

**没有一条阈值线能同时做到“不误拒有答案题”和“拦住所有无答案题”。** 这不是调参能解决的问题，是 rerank 分数的语义决定的：它衡量“话题相关性”，不衡量“是否包含答案”。

## 决策：两层拒答

1. **检索闸门**：`retrieval_gate_rerank_score = 0.01`。只拦“完全无关”的检索结果，直接返回固定拒答文案，不调用云端（省一次调用）。0.01 取在最弱有答案题（0.017）之下并留出余量；在这一阈值下 5 道无答案题被无风险拒掉，误拒 0。
2. **生成层拒答**：通过闸门的片段交给模型，系统 prompt 要求“资料不足时直接说明资料中未找到足够依据”。话题相关但缺少具体事实的无答案题（q33/q37 等）由这一层拦下。
3. 两层都计入端到端指标；只用闸门算出的“拒答率”单列，避免把生成层的功劳算到阈值头上。

## 关键发现 2：rerank 与融合召回是互补的，不是替代关系

rerank 提升了 MRR（0.806 → 0.844），但把 2 道语义改写题的正确片段挤出了前 5（Recall@5 91.1% → 87.2%）。试过的融合变体：

| 方案 | Hit@5 | Recall@5 | MRR@5 |
| --- | --- | --- | --- |
| rerank 直接排序（选择） | 93.3% | 87.2% | **0.844** |
| 三路 RRF（dense + sparse + rerank） | 96.7% | 90.6% | 0.767 |
| Borda（融合排名与 rerank 排名取平均） | 96.7% | 92.2% | 0.807 |
| 固定保留融合前 3 名 | **100%** | **92.8%** | 0.814 |

“固定保留前 3 名”指标最好，但它等于不信任 rerank 的头部判断，规则也难以解释；三路 RRF 把 MRR 拉低 0.08。最终选择标准的 rerank 排序：MRR 更高意味着最相关片段排在前面，生成时更可能被优先引用；Recall@5 仍满足 ≥ 0.8 的验收线。这个取舍记录在此，后续若发现漏召回影响回答质量，可切换到 Borda。

## 关键发现 3：引用精确率取决于标注口径，最严格的“逐句支撑”仍未覆盖

同一轮生成结果，用三种口径算出来的数完全不同：

| 口径 | 结果（宏 / 微） | 含义 |
| --- | --- | --- |
| 只认 gold | 65.3% / 50.0% | 度量“是否只引用 minimally 标注的那一段”，对多部分问题和合理补充引用一律判错 |
| gold ∪ acceptable | **89.2% / 84.3%** | 度量“引用是否指向能回答该问题的片段”，是本阶段采用的验收口径 |
| 逐句支撑（人工 / NLI） | 未做 | 度量“每个编号是否支撑它所在的那句话”，最贴近“引用准不准”的直觉，但需要句子级判断 |

仍低于 90% 的 0.8 个百分点来自**生成端的过度引用**：模型对窄问题也会给出 3～5 条引用。例如 q22（中文 BM25 注意事项）一条回答引用了全部 5 个片段，其中 4 个只是 BM25 的通用背景或 Qdrant 配置细节，没有涉及中文语料的特殊问题；q26（8GB 显存如何安排）引用 3 条，其中“性能基线”讲的是延迟、没有给出内存安排。这不是检索错误，也不是标注遗漏：那几条确实没有被用来支撑答案的关键句。

尝试过在系统 prompt 里加一句“只标注真正支撑该句的片段，不要罗列未使用的编号”，同一标注下精确率从 89.7% 变为 89.2%（单轮运行，属噪声范围），因此**不能声称该 prompt 有效**；它保留是因为语义更明确、不改变召回与拒答，但没有作为达标手段。

结论：在“规则匹配、无模型裁判”的约束下，89.2%（宏）是本阶段能给出的最好数字，比 90% 的验收线低 0.8 个百分点。要真正回答“引用是否准确”，需要逐句标注或 NLI 裁判（口径 3），超出本阶段范围；引用编号有效性（100%，由协议保证）与引用召回（93.3%）不受此限制。

## 复现

```bash
.venv/Scripts/python.exe scripts/eval_retrieval.py         # 离线：三种模式 + 阈值扫参
.venv/Scripts/python.exe scripts/eval_retrieval.py --full  # 追加云端生成评测（会把 top-5 片段发给 DeepSeek）
```

输出 `docs/eval/stage2-report.json`（含逐题明细、每路排名与分数）与 `stage2-report.md`（汇总表）。评测脚本与生产链路共用 `retrieve` / `should_refuse` / `build_messages`，避免“评测代码和线上代码不是一套”。

## 后果

- 参数调整（top_n、rrf_k、闸门阈值、rerank 模型）必须重跑评测并更新本 ADR 与报告。
- 评测集扩充或分块参数变化时，gold 与 acceptable 引文需仍能唯一定位；脚本会校验并以退出码 2 失败。
- 引用精确率对 `acceptable` 标注敏感，新增题目要同时标注可接受片段，否则数字不可比。
- 云端 `--full` 会产生真实 API 费用与片段出站，默认关闭，需要显式加参数。
