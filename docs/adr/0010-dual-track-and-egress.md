# 0010 · 双轨生成与出站策略

- **状态**：已接受（阶段 3，2026-10-25）
- **日期**：2026-10-25
- **决策者**：项目作者 + 协作代理

## 背景

项目定位要求"原始文档始终留在本机，哪些内容可以发给云端由我控制；生成支持双轨切换：云端默认、本地断网可用，随时可切、不锁死"。这带来三个必须回答的问题：

1. 两条轨道如何做到"同一套接口"，而不是两套代码路径？
2. 出站控制放在哪一层，才能既好用又可证明？
3. 本地轨道与本地模型共存时，8GB 显存怎么分配？

## 决策

### 1. 一个协议，两个实现

`ChatProvider` 协议只要求四件事：`name`、`model`、`available()`、`stream_chat()` 逐段返回文本。`DeepSeekProvider` 与 `OllamaProvider` 各自实现，SSE 事件结构、引用解析、指标埋点都不区分轨道。前端的轨道切换只改一个请求字段。

Ollama 的请求体显式带 `think: false`：qwen3.x 默认会流式输出思考过程，打开后首 token 变成"开始思考"而不是"开始回答"，首 token 指标失去意义。

### 2. 轨道解析优先级：请求 > 会话 > 环境默认

```
payload.track  →  conversation.track  →  settings.default_track
```

- 会话创建时写入当时生效的轨道，之后同一会话默认沿用它，避免"上一轮云端、下一轮本地"的静默漂移。
- UI 切换轨道时下一次请求带上 `track`，服务端更新会话记录。切换不需要重启进程，也不影响其他会话。
- 老会话（阶段 2 创建）的 `track` 为 NULL，按环境默认值处理。

### 3. 重排按轨道分设备

云端轨道保留 CUDA 重排；本地轨道用 CPU 重排（`RERANK_DEVICE_LOCAL=cpu`）。两个实例按需懒加载，进程只加载实际用到的那个。

理由：本地轨道里 Ollama 要用 3.1GB 显存跑 4B 模型，再叠加 bge-m3（0.7GB）与 CUDA 重排（约 2.3GB）会把 8GB 显存压到边缘。把重排挪到 CPU 后，本地轨道显存只留给生成模型，两条轨道互不驱逐。

代价是重排延迟从 ~0.3s 变成 ~2.1s，直接算进本地首 token（实测 p50 2.7s，仍低于 5s 验收线）。

### 4. 出站策略在服务端，且分三层

| 层 | 机制 | 用户可见 |
| --- | --- | --- |
| 轨道 | `track=local` 时只调用 `127.0.0.1` | 右上角开关、消息上的「本地 · 零出站」徽标 |
| 来源黑名单 | `sources.egress_allowed=false`，云端检索后按 `document_id` 剔除命中并重排引用编号 | 左侧每个资料源的开关；回执里的"已剔除 N 段" |
| 每轮开关 | `skip_egress=true` 时只检索、不调用任何生成模型 | 输入框「本次不上传（仅检索）」 |

关键取舍：

- **过滤在服务端**。前端开关只是入口，真正的过滤发生在 prompt 构造之前；即使绕过 UI 直接调 API，被禁止的目录也不会出站。
- **过滤后重排引用编号**。否则会出现 `[1] [3]` 这样的空号，模型会照抄。
- **全部命中被拦时给专用文案**，不能说"资料中未找到"——资料存在，是策略拦下的。这条被写进测试。
- **「仅检索」开关不跨轮记忆**，每轮默认关闭，避免"以为关了其实没关"。

### 5. 回执与埋点

每次回答的 `citations` 事件都带 `egress` 回执：`track / enabled / chunks / files / chars / blocked_chunks / blocked_files / skipped`。`done` 事件带 `ttft_ms / total_ms`，助手消息把同样的指标写进 `messages.metrics_json`（含检索耗时与重排设备）。

回执是给用户看的"这一轮到底发了什么"，指标是给验收与面试用的数据来源。两者都来自服务端实际执行的路径，不是前端推算。

### 6. 迁移策略

阶段 3 给已有表加了列（`sources.egress_allowed`、`conversations.track`、`messages.track`、`messages.metrics_json`）。`create_all()` 不会修改已存在的表，因此启动时读 `PRAGMA table_info`，缺列就 `ALTER TABLE ADD COLUMN`，幂等。

没有引入 Alembic：目前只有"加可空列/带默认值的列"这一种变更，SQLite 原生支持；真正的迁移编排（改类型、拆表、回滚）留到阶段 5 工程化时再上，避免现在就多一个讲不清的组件。

## 备选与取舍

| 决策点 | 备选 | 为什么没选 |
| --- | --- | --- |
| 双轨抽象 | LiteLLM / OpenAI 兼容代理统一两路 | 多一层依赖，且代理层不暴露 Ollama 的 `think` 开关；薄协议只有 30 行，面试时能讲清每个字段 |
| 轨道粒度 | 全局 env 开关 | 改一次要重启，且无法"这个会话本地、那个会话云端"，不满足"不锁死" |
| 出站过滤位置 | 前端过滤 / 检索层过滤 | 前端不可信；检索层过滤会让本地轨道也拿不到内容。放在"检索之后、构造 prompt 之前"最准确 |
| 本地重排 | 继续用 CUDA / 关闭重排 | CUDA 会与本地模型抢显存（实测云端重排会被拖慢到 0.75s）；关闭重排会损失本地轨道的引用质量 |
| 「不上传」交互 | 发送前弹窗预览片段再确认 | 真正的"发送前预览"需要两段式请求（先检索、再确认生成），当前实现选择了更简单的"先勾再发 + 事后回执"；收益与复杂度不匹配 |
| 指标存放 | 只写日志 | 日志会轮转、跨进程；写库后可以直接 SQL 统计两条轨道的首 token 分布 |

## 实测数据（2026-10-25）

同一台机器（RTX 5060 Laptop 8GB / 16GB RAM），同一问题集，每轨道 3 次：

| 指标 | 云端轨道（CUDA 重排） | 本地轨道（CPU 重排） |
| --- | --- | --- |
| 首 token p50 | **1.64 s**（本地模型驻留时）/ 1.35 s（卸载后） | **2.71 s** |
| 总耗时 p50 | 3.00 s | 5.60 s |
| 重排 p50 | 0.75 s / 0.37 s | 2.13 s |
| 出站 | 5 段 / 2 文件 / 918 字符 | 0 |

- GPU 争用是真实存在的：本地模型在显存里时，云端轨道的 CUDA 重排从 0.37s 升到 0.75s；Ollama 空闲卸载后恢复。首 token 仍在 2s 验收线内。
- 本地轨道 3 次均只观测到环回连接（Ollama `127.0.0.1:11434` 与本机 Qdrant），见 `scripts/verify_offline.py` 的输出。

## 后果

- 新增轨道必须实现 `ChatProvider` 协议；`chat.py` 不需要知道具体是实现。
- 出站策略的改动必须同步更新 `egress` 回执与测试（`test_egress.py` 覆盖拆分、编号、回执计数）。
- 本地轨道的回答质量低于云端是预期内的：4B 模型会啰嗦、偶发混用片段。演示时应把这一点讲出来，而不是隐藏。
- `messages.track` 存字符串而非外键，轨道只有两个值；若将来出现第三种轨道，需要同步迁移与前端枚举。
- 每次云端请求都会多一次 DB 查询（黑名单文档 ID 集合）。当前规模下可忽略；若文档数达到十万级，应缓存或改为检索时过滤。
