# 0012 · 文档格式扩展与引用定位

- **状态**：已接受（阶段 5，2026-10-25）
- **日期**：2026-10-25
- **决策者**：项目作者 + 协作代理

## 背景

阶段 1～4 只索引 `.md` / `.txt`。"个人知识代理"的真实资料里有 PDF（电子书、论文、导出报告）、docx（别人发来的文档）和代码。这些格式有两个新问题：

1. **解析**：PDF 没有"行"的概念，文本是坐标块；docx 有真正的样式层级；代码需要按语义单元切分，否则一个分块可能横跨两个函数。
2. **引用**：已有的引用是"文件 + 小节 + 行号"。对 PDF 说"第 128–134 行"既不可核对也无意义——用户打开 PDF 看到的是页码。

另一个隐含问题：一旦分块方式随文件类型变化，评测集的 gold（逐字引文 → 分块）必须仍然能解析到唯一分块，否则历史评测数据失效。

## 决策

### 1. 解析器返回"文本 + 分块模式 + 定位信息"，而不是纯文本

`ParsedDocument` 现在携带：

| 字段 | 作用 |
| --- | --- |
| `text` | 规范化后的文本（`\n` 行尾），chunker 唯一输入 |
| `mode` | `markdown` / `text` / `code`，显式表达"该怎么切" |
| `doc_type` | `markdown` / `text` / `pdf` / `docx` / `code`，用于日志与统计 |
| `page_starts` | PDF 每页起始字符偏移，chunker 据此给每个分块标页码 |
| `page_count` | 写入 `documents.page_count`，用于解释"有页但没有文本" |

原来的 `markdown: bool` 被 `mode` 取代：docx 的 `doc_type` 是 `docx`，但分块模式是 `markdown`（Word 标题被转换成 `#` 标题），两者本来就不是一回事。

### 2. PDF：PyMuPDF 按页取块，每页单独一节

- 用 `page.get_text("blocks")` 取文本块，跳过图片块（`block_type != 0`），块之间用空行连接 —— 于是每块天然是一个"段落"，沿用已有的段落打包逻辑。
- **分块不跨页**。这一条是刻意的：允许跨页时引用会显示"第 3–4 页"，读者仍然不知道句子在哪；代价是跨页段落被切成两段。
- 页码通过 `page_starts` + `bisect` 得出，分块在页内硬切（超过 `CHUNK_MAX_CHARS`）时页码仍然正确。

### 3. docx：标题转成 markdown 标题，表格按行保留

`Heading N` / `标题 N` / `Title` 转换成 `#…######`，正文段落原样保留，表格每行拼成 `a | b | c`。这样 docx 复用 markdown 的分块路径，引用里能出现 `部署指南 > 回滚` 这样的标题路径，而不是一个匿名行号区间。

### 4. 代码：扩展名白名单 + 顶层符号切节

- 白名单 23 种后缀（Python / JS / TS / Go / Rust / Java / C 系 / shell / SQL / HTML / CSS / Vue / YAML / TOML / JSON / INI）。**不做 AST**：解析器只需知道"哪一行是顶层声明"，正则足够，代价是极少数写法（例如宏生成的函数）识别不到，退化为按空行分块。
- 只在列 0 的位置匹配符号（`def` / `class` / `func` / `fn` / `impl` / `interface` / `struct` / `export` …），嵌套方法不会被当成新节。
- 声明行保留在正文里（它是代码的一部分），同时作为 `heading`。硬切产生的后续分块因此仍带着"我属于哪个函数"。

### 5. 引用新增 `ordinal` / `page` / `page_end`

- `ordinal`：分块在文档内的序号（0 起），前端显示"第 K 块"。
- `page` / `page_end`：PDF 页码（1 起）。有页码时前端显示「第 N 页 · 第 K 块」，没有时继续显示行号。
- 送进 prompt 的上下文里，PDF 写"页码：N"而不是行号 —— 让模型复述时有意义的位置信息。
- 旧消息里存的引用没有这些字段，前端按"缺字段就不显示"降级，不报错。

### 6. 扫描版 PDF 明确失败，不索引空文档

`page_count` 页但提取不到文本 → 抛 `UnsupportedDocumentError("PDF 共 N 页，但没有可提取文本（可能是扫描版，当前不做 OCR）")`，计入 `failed` 与错误列表。OCR 需要额外模型与数倍的处理时间，不在首版范围。

## 备选与取舍

| 决策点 | 备选 | 为什么没选 |
| --- | --- | --- |
| PDF 解析 | pdfplumber / pypdf / Unstructured | PyMuPDF 快、按块取文本且能拿到坐标；pdfplumber 更慢且内存占用高；Unstructured 会引入一堆重依赖 |
| PDF 分块 | 允许跨页 + 显示页码区间 | 引用精度下降；"第 3–4 页"对读者没有定位价值 |
| 引用定位 | 只给页码 / 只给行号 / 页码 + 块号 | 只给页码时同页多块无法区分；行号对 PDF 是解析器的内部产物 |
| docx | 纯文本提取（丢标题） | 丢失结构后引用无法指向小节，碎片化严重 |
| 代码切分 | tree-sitter AST | 多语言 AST 依赖体积大、每种语言一套查询；白名单 + 正则覆盖 90% 场景，且解释成本低 |
| 代码切分 | 按固定长度硬切 | 会把两个函数切成一块，检索到的片段无法独立理解 |
| OCR | 首版接入（PaddleOCR / Tesseract） | 模型体积与误识别风险高；先让"没有文本层"这件事显式失败，需要时再加 |

## 实测（2026-10-25，本机）

| 场景 | 结果 |
| --- | --- |
| 3 页中文 PDF（`examples/formats/localmind-runbook.pdf`） | `page_count=3`，3 个分块，页码 1 / 2 / 3，`ordinal` 0 / 1 / 2 |
| 带标题与表格的 docx | 4 个分块，标题路径如 `知识库交付清单 > 一、资料入库`，表格行保留为 `检查项 \| 命令 \| 期望结果` |
| 只检索提问"备份要备份哪些东西？" | top1 = PDF 第 1 页，重排分 0.942（其余命中 0.11 以下） |
| 扫描版 PDF（无文本层的两页） | 抛出明确错误，`scan` 计入 `failed`，不产生分块 |
| 旧评测集回归 | 40 题 gold 全部仍能解析到唯一分块；Recall@5 与阶段 2 一致（87.2%） |

评测集 gold 用逐字引文而非分块 id，是阶段 2 就做对的一件事：这次改了解析器与分块参数，评测集不需要改一个字。

### 为什么最终保留"每页单独分块"（2026-10-25 决策记录）

"不跨页"是个有代价的选择，所以在阶段 5 收尾时做了一次量化：把仓库里 10 篇笔记拼成一份 10 页中文 PDF（按固定字符数切页，页边界落在段落中间），用同一套 chunker 分别测两种策略：

| 页长（字符/页） | 按页分块 | 允许跨页 |
| --- | --- | --- |
| ~780 | 19 块，中位 431 字，**6 块 < 200 字（32%）** | 13 块，中位 587 字，0 个小块 |
| ~1000 | 15 块，中位 451 字，0 个小块 | 13 块，中位 577 字 |

代价是**分块数多约 46%**，且页长不是分块上限整数倍时每页会剩一个 50～200 字的尾巴块（约三分之一的页面）。

仍然保留，理由：

1. 短块并不意味着检索弱。演示 PDF 每页约 200 字（正好全是短块），问「备份要备份哪些东西？」top1 重排分 **0.942**，第二名 0.11；稠密检索对短文本不敏感，损失的只是块内上下文。
2. 代价有上限且可量化：500 页的书大约 1700 → 2500 个向量，对 Qdrant 不构成压力。
3. 单页引用直接对应"依据来自哪里"这个产品承诺；跨页引用会让读者自己去翻两页。
4. 现有评测集是 markdown 的，没有 PDF 题的对比数据；在缺证据时引入更复杂的规则，是用确定的成本换不确定的收益。

**重新评估的触发条件**（满足任意一条就改）：

- 评测集补入约 10 道 PDF 题后，按页分块的 Recall@5 明显低于 markdown 的 87.2%；
- 实际使用中大量出现 50 字以下的碎片块（说明 PDF 排版特殊，例如图表页居多）。

两种改法都不需要迁移：`chunks.page_end` 已存在，UI 已支持页码区间显示，改的只是 chunker 是否在页边界 flush。

## 后果

- PDF 的分块粒度由页决定：一页很长时会切成多块，一页很短时只有一个块，与正文的语义边界不完全对齐。
- 代码文件按语言白名单收录；不在白名单里的后缀（如 `.ipynb`、`.proto`）需要显式添加。
- 引用在 UI 上有两种形态（行号 / 页码），前端必须同时处理；`locationLabel()` 是唯一入口。
- `Ordinal` 依赖重新索引：阶段 5 之前入库的分块 payload 里没有该字段，`--force` 重建后一致（旧引用不受影响，因为块号只在 PDF 引用里显示）。
- 扫描版 PDF 目前只能靠用户换文件或另装 OCR 工具；错误信息里写明了原因。
