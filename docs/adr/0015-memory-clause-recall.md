# 0015 · 记忆召回：按子句拆查询，而不是按 key 查

- **状态**：已接受（阶段 6，2026-10-25）
- **日期**：2026-10-25
- **决策者**：项目作者 + 协作代理

## 背景

阶段 4 的记忆召回是"一条消息、一次向量查询"。当时的已知限制写得很清楚：一句话问两件事时只召回其中一件（实测"我住哪、用什么语言"只召回城市，0.54）。

阶段 6 原本的计划是加一条 **key 精确查找**：抽取时已经强制要求稳定的 key，`memories` 表上有 `(key, status)` 联合索引，按 key 查是一次 SQLite 查询、零向量计算。看起来是便宜的补强。

## 先测量，再否掉原方案

用库里 4 条真实记忆的 key 做匹配（key 以 `用户的{key}` 模板嵌入，与问题向量算余弦），问题「你还记得我住哪、用什么语言吗？」：

| 候选 | key 相似度 | 记忆正文相似度 |
| --- | --- | --- |
| **技术栈偏好（正确答案）** | **0.436** | 0.448 |
| 回答风格偏好（无关） | 0.485 | 0.393 |
| 性别（无关） | 0.485 | 0.494 |

正确答案的分数**低于两个无关属性**，而且低于现有的 0.5 阈值。换三种 key 模板（裸 key、`用户的{key}`、`用户的{key}是什么？`、`关于{key}的记忆`）在 5 个正例 + 8 个反例上重测，正例最低 0.51～0.52、反例最高 0.48～0.53，**正反例间距只有 0.03～0.04**。

原因不复杂：一句话问两件事时，**问题向量本身就是两个意图的平均**。key 匹配用的是同一个平均向量，因此它和正文召回被同样的稀释伤害——加一条 key 路径并没有改变"单向量"这个根因。

## 决策：按子句拆查询，再合并

`split_question()` 把问题按标点（`，,、；;`）和无歧义连词（`以及`、`还有`、`或者`、`还是`）拆成最多 3 条子句；每条子句各做一次嵌入与向量检索，命中按 `memory_id` 合并、保留最高分，排序后受 `MEMORY_TOP_K` 限制。阈值仍是 `MEMORY_MIN_SCORE=0.5`，没有新增参数。

不拆分单独的「和」：它出现在常见词内部（和平、柔和、总和），拆错只会多一次匹配不到任何东西的嵌入。

实测（同一批记忆，改前 → 改后）：

| 问题 | 改前（整句一次查询） | 改后（按子句） |
| --- | --- | --- |
| 你还记得我住哪、用什么语言吗？ | 所在城市 0.545 ✅、技术栈 0.448 ❌ | 所在城市 **0.555** ✅ + 技术栈 **0.649** ✅ |
| 我住哪个城市、平时用什么语言？ | 0.660 / 0.530（勉强过线） | 0.743 / 0.630 |
| 我平时用什么语言、喜欢什么样的回答？ | 回答风格 0.700 ✅、技术栈未进前 3 | 技术栈 **0.644** ✅ + 回答风格 **0.688** ✅ |

端到端：改前问「你还记得我住哪、用什么语言吗」，模型回答"记忆里没有关于你语言偏好的记录"；改后回答"你住在杭州，后端主要用 Go 语言写"。

## 备选与取舍

| 决策点 | 备选 | 为什么没选 |
| --- | --- | --- |
| 补强方式 | key 精确查找（原计划） | 实测正确 key 的相似度低于无关 key，正反例间距 0.03 |
| 补强方式 | 用模型把问题拆成子问题（LLM query decomposition） | 每轮多一次模型调用；本地 4B 上还要承担解析失败的风险。规则拆分在中文标点上已经够用 |
| 补强方式 | 把 `MEMORY_TOP_K` 调大 / 降低阈值 | 只是让更多低分记忆进上下文，解决不了"正确答案分数低于无关项"的排序问题 |
| 补强方式 | 多向量表示（ColBERT 一类） | 需要换嵌入方案与存储格式，成本远超这个功能的价值 |
| 拆分规则 | 也拆「和」 | 词内误伤（和平、柔和），收益不抵噪声 |
| 合并方式 | 每个子句各注入 top-1 | 平均问法下会丢掉同义 key 的第二条（如"居住地"与"所在城市"并存的情况） |

## 实测数据（2026-10-25）

- 记忆场景评测 `docs/eval/memory-report.md`：**7/7 通过**，其中 `memory-3`（一句问两个属性）与 `memory-4`（换个说法问同一属性）是阶段 6 新增的回归场景。
- 额外延迟：每多一条子句多一次本地嵌入（约 50 ms）与一次向量查询；单子句问题（大多数）与改前完全一致。
- 噪声：合并后召回条数变多，0.5 阈值下会带进弱相关条目（问语言时召回"性别"0.57）。它按分数排在后面，且记忆区在 UI 里可展开核对，因此接受；要收紧需引入相对分数间隔，那是另一个取舍。

## 后果

- 没有标点的复合问题（"我住哪用什么语言"）不会被拆，仍走单次查询——这是规则拆分的边界。
- 记忆召回从"一次查询"变成"最多三次查询"，日志里记录 `clauses` 与 `candidates` 便于排查。
- 删除一条记忆**不会**改写曾提到它的会话摘要（`memory-7` 的证据里 `summary_still_mentions_city=true`）。摘要不是事实来源，但确实会让被删的信息继续出现；修它需要"删除时按字符串改写摘要"这类脆弱逻辑，因此只记录、不实现，README 写入已知限制。
- 这套"拆子句再合并"的思路与文档层的混合检索是同一类做法（多路召回 + 合并），但层次不同：文档层合并两路**不同性质**的检索，记忆层合并的是**同一问句的不同意图**。
