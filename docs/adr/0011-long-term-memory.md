# 0011 · 长期记忆：抽取、冲突、时间与出站

- **状态**：已接受（阶段 4，2026-10-25）
- **日期**：2026-10-25
- **决策者**：项目作者 + 协作代理

## 背景

项目目标里有两条超出普通 RAG 的要求：

- "要能回答几个月前我告诉过你的事"——跨会话的事实与偏好；
- "资料里找不到时明确说找不到"——所以记忆必须与文档引用分开表达，不能混进 `[n]` 引用体系。

同时隐私承诺不能因为记忆而破：原始文档不离机、只有明确列出的内容才能出站、本地轨道零出站。这意味着记忆的**写入**（抽取）和**读取**（召回注入）都要重新回答"什么东西会离开这台机器"。

## 决策

### 1. 每轮答完异步抽取，跟随轨道

`after_turn` 由 `TaskRunner` 在 SSE `done` 之后 `spawn`，不阻塞回答；失败只写日志与消息指标（`messages.metrics_json.memory`），绝不在对话流里报错。

抽取使用的模型跟随本轮轨道：

| 轨道 | 抽取调用 | 读取内容 | 新增出站 |
| --- | --- | --- | --- |
| 云端 | DeepSeek | **只读用户这一条消息** | 无：这条消息为了回答已经发过一次 |
| 本地 | Ollama（本机） | 同上 | 0 |

会话摘要需要读两侧内容（用户 + 助手），所以单独记录在 `metrics.memory.summary` 里，并在日志里注明 `chars`，方便审计"多发了什么"。

嵌入始终走本机 bge-m3，记忆文本永远不为了向量化而外发。

### 2. SQLite 是唯一事实来源，Qdrant 只存活跃向量

- `memories` 表保存全部行（含已替换的旧值），字段：`kind / key / content / occurred_at / created_at / source_conversation_id / source_message_id / status / superseded_by / embedding_ok`。
- Qdrant 集合 `localmind_memories` 只放 `status=active` 的向量；被替换的旧行保留在 SQLite 供面板查看，向量随即删除。
- 召回时先向量检索（多取 2 倍候选），再回 SQLite 按 `status=active` 过滤。这样即使向量与库在某一刻不一致，也不会把已被替换的记忆注入 prompt。

先写库、后写向量。向量写失败时把该行标为 `embedding_ok=false`（面板可见"未入索引"），而不是丢掉用户说过的话。

### 3. key 是唯一身份，同 key 覆盖并保留历史

抽取器输出 `{kind, key, content, occurred_at}`。`key` 是稳定的属性名（"所在城市"、"技术栈偏好"），抽取 prompt 会把**已有的 (kind, key) 对**喂回去，要求原样复用。

覆盖条件只看 `key`，不看 `kind`：实测中抽取器把同一个属性在不同轮次标成 `preference` 和 `fact` 各一次，若按 `(kind, key)` 匹配就会留下两条互相矛盾的活跃记忆，模型只能在回答里说"你给过两种说法"。改成 key 唯一后，kind 只影响面板标签，不再影响身份。同一轮内出现的重复 key 也只保留第一条。

被覆盖的行 `status=superseded`、`superseded_by` 指向新行；删除新行时清空该指针，旧行仍留在历史里。这一条同时满足"冲突更新"与"可回看我说过什么"。

### 4. 两种时间，存 UTC、按本地日期展示

- `occurred_at`：事件发生时间，由模型抽取（"去年八月"按【今天】换算）；未来日期一律丢弃（几乎都是幻觉）。
- `created_at`：记录时间，写入时取 UTC。

SQLite 不保留时区，SQLAlchemy 读回来的是 naive UTC。因此所有面向用户和模型的日期都经过 `app/timeutil.py`：API 输出带 `+00:00` 的 ISO 字符串，prompt 里写用户的**本地**日历日期。实测前一天 18:39 UTC 记录的记忆，第一次实现里被模型说成"2026-10-24"，换算成本地日期后是 2026-10-25，与用户感知一致。

### 5. 摘要每 6 条用户消息滚动一次，边界用条件更新抢占

摘要把"之前的摘要 + 最近 12 条消息"合并成一段 `kind=summary`、`key=summary:<conversation_id>` 的记忆，旧版本被覆盖。它解决两类问题：长会话的历史消息被 `CHAT_HISTORY_TURNS` 截断；跨会话回忆会话级结论。

触发条件不用 `count % 6 == 0`：相邻两轮的后台任务会重叠，实测两轮同一会话的抽取任务交错时，两个任务都读到 `count=6`，于是写了两次同边界摘要（旧值立刻被新值覆盖，但白花一次调用）。现在把"已摘要到第几条用户消息"存在 `conversations.summarized_user_messages`，用 `UPDATE ... WHERE summarized_user_messages = last` 抢占，抢不到就跳过；生成失败时把边界还回去，下一轮重试。同类会话的后台任务还用一把按会话的 `asyncio.Lock` 串行化，避免同一 key 的两次抽取互相看不见对方。

"没有需要长期保留的内容"这类空摘要视为边界已处理，不回退：重试只会重复烧调用。

### 6. 注入与回答规则：记忆不是引用

召回的记忆以独立段落 `【记忆】` 进入 prompt，提示词明确：

- 记忆只用于回答"我以前说过什么 / 我的偏好是什么"；
- 记忆**不带 `[n]` 编号**，引用只来自文档；
- 记忆与文档冲突时以文档为准，并指出冲突。

前端同样分开展示：回答头部有「记忆 N」徽标，右侧栏分成「召回的记忆」与「资料片段」两段，记忆卡片显示 key、类型、日期与相似度分数。

召回阈值 `MEMORY_MIN_SCORE=0.5`，本轮实测：直接问偏好 0.80、问城市 0.54～0.63、无关问题（"预算多少""猫叫什么"）0 条。当有记忆被召回时，第一层拒答闸门被解除——否则"我之前说过什么"这类问题会因为本地资料无关而被直接拒答；安全性由第二层（模型按提示词判断记忆是否够用）兜底。

### 7. 记忆也计入出站回执

`egress` 回执新增 `memories` 与 `memory_chars`，云端回执的 `chars` 已包含记忆正文。用户能看到"这一轮发了几条记忆、多少字符"，与片段计数并列。管理面最小化：左侧面板只能查看（可分页查看已替换的旧值）和删除，不提供编辑——编辑等于手写记忆，会引入一套新的校验与冲突规则，收益不匹配。

## 备选与取舍

| 决策点 | 备选 | 为什么没选 |
| --- | --- | --- |
| 抽取时机 | 每轮同步抽取 / 定时批处理 | 同步会把延迟加到回答上；批处理会让"刚说过就忘了"，演示效果差 |
| 抽取输入 | 用户+助手两侧 / 只用户 | 助手内容可能是幻觉，写进记忆会被重复放大；只读用户消息也让云端的"新增出站"为 0 |
| 存储 | 只用 Qdrant payload / 只用 SQLite | 纯向量库没有事务与约束，覆盖历史难查；纯 SQLite 无法语义召回。拆分后各司其职 |
| 冲突判定 | `(kind, key)` / 语义相似度去重 | `(kind, key)` 被实测证伪（kind 会漂移）；语义相似度去重误伤率高（"技术栈偏好"与"常用语言"会被合并），先不做 |
| 时间 | 只存 `created_at` / 只存 `occurred_at` | 只存记录时间回答不了"什么时候的事"；只存事件时间则大多数记忆没有日期 |
| 摘要触发 | `count % N` / LLM 判断"该总结了" | 前者有实测竞态；后者每轮多一次调用且不可预测，面板与测试都无法断言 |
| 管理界面 | 可编辑记忆 / 只读+删除 | 可编辑要再定义一套校验与冲突语义；删除已覆盖"说错了，忘掉"这个真实需求 |
| 摘要粒度 | 每会话一条 / 每用户一条跨会话 | 跨会话合并属于"用户画像"，与事实/偏好职责重叠，第一版不引入 |

## 实测数据（2026-10-25，RTX 5060 Laptop 8GB / 16GB RAM）

| 场景 | 结果 |
| --- | --- |
| 一轮陈述抽取出 3 条记忆（城市 / 技术栈 / 回答风格） | 云端抽取 1.27 s，3 条全部 `embedding_ok=true` |
| 跨会话提问"我之前告诉你我住哪" | 召回 1 条（0.632），回答带本地日期，出站回执 `memories=1, memory_chars=7` |
| 同 key 更新（Python → Go） | 旧行 `superseded`、`superseded_by` 指向新行，向量集合只剩 1 条；新会话再问只召回 Go |
| kind 漂移（同一 key 被标成 fact / preference） | 覆盖逻辑按 key 命中，仅一条 active（修复前会留下两条矛盾记忆） |
| 一轮无关问题（"预算多少"） | 召回 0 条，两层拒答正常；"分块策略"类问题会召回内容相关的摘要（0.55～0.59） |
| 本地轨道提问 | 出站回执 `enabled=false`，召回 1 条记忆，首 token 3.49 s，抽取在本机完成（554 ms） |
| 6 轮摘要 | 写入 1 条 `summary:<cid>`；修复前同一轮次会写 2 条 |

抽取耗时、召回条数、摘要状态都写进 `messages.metrics_json.memory`，可直接用 SQL 统计，不需要翻日志。

## 后果

- 记忆质量取决于抽取 prompt 与模型。4B 本地模型的 JSON 合规性明显低于云端，`parse_drafts` 因此接受围栏代码块、逐条丢弃非法项、永不抛异常。
- 每条记忆都会被向量化并进入召回池；如果用户大量陈述临时信息，面板里会堆积噪音，删除是目前唯一的清理手段。批量清理/自动过期留到需要时再做。
- 会话摘要会读到助手回答，属于"额外读取本地内容"，但没有新增出站（摘要调用与生成走同一轨道、同一服务）。
- 面板刷新有 4 秒延迟（抽取在后台跑），因此保留手动「刷新」按钮；这是刻意选择，而不是轮询。
- `summarized_user_messages` 是阶段 4 新增的列，沿用阶段 3 的 `PRAGMA table_info` + `ALTER TABLE ADD COLUMN` 机制，Alembic 仍留到阶段 5。
