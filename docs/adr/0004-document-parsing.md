# 0004 · 文档解析方案

- **状态**：已接受（OCR 暂不纳入）
- **日期**：2026-10-24
- **决策者**：项目作者 + 协作代理

## 背景

资料规模 1k～5k 份，格式以 md/txt/pdf/docx/代码为主。解析质量直接决定分块与检索上限；但解析不是本项目的主要亮点，不能挤占检索与双轨的时间。

## 决策

| 格式 | 方案 |
| --- | --- |
| md / txt | 原生读取，保留标题层级 |
| pdf | PyMuPDF (`pymupdf`) 抽取文本与页码 |
| docx | `python-docx` 抽取段落 |
| 代码 | 按文本读取，按语言与函数/段落边界分块 |

- 每条 chunk 保留：源文件路径、页码/段落号、字符偏移、解析器版本。
- 扫描版 PDF（无可抽取文本）标记为 `needs_ocr`，首版不处理，UI 明确提示。
- OCR 作为阶段 5 的可选扩展，不进入首版验收。

## 备选与取舍

| 方案 | 取舍 |
| --- | --- |
| **PyMuPDF + python-docx（选择）** | 轻量、成熟、快；数字版 PDF 足够。表格与扫描件弱。 |
| Docling | 版面、表格、OCR 更强，输出结构化；但依赖重、速度慢、调试成本高，容易拖慢阶段 1。 |
| Unstructured | 格式覆盖广；依赖多、输出不稳定、镜像大。 |
| 只做 md/txt | 最快，但 1k～5k 资料中 PDF 占比通常不低，演示不真实。 |

## 后果

- 表格与多栏 PDF 可能出现文本顺序问题；阶段 2 的评测集要包含这类样本，暴露问题而不是隐藏。
- 解析失败不静默跳过：记录失败原因与文件路径，UI 可查看。
- 解析器版本写入 chunk 元数据，便于后续重建索引。
