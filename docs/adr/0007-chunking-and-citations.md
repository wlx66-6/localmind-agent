# 0007 · 分块与引用：标题感知分块 + 行号定位

- **状态**：已接受（阶段 1，参数待阶段 2 评测校准）
- **日期**：2026-10-25
- **决策者**：项目作者 + 协作代理

## 背景

项目要求"回答能说明依据来自哪些资料"，且引用要经得起核对。引用可用性取决于两件事：分块是否带着足够的主题信息；分块能否映射回原文的精确位置。个人笔记以 Markdown 为主，天然有标题层级。

## 决策

1. **按标题切节**：`#`/`##`/… 开启新节，标题路径（`A > B`）随分块保存。
2. **节内按段落打包**：段落装入不超过 `CHUNK_MAX_CHARS`（默认 600 字符）的分块；单段超长时先按句末标点切，仍超长才硬切，硬切时带 `CHUNK_OVERLAP`（默认 100 字符）重叠。
3. **重叠只用在强制切分**：正常段落块不携带重复内容，避免索引体积和召回冗余。
4. **嵌入文本 = 标题路径 + 正文**：让"同名但不同小节"的片段可区分；返回给用户与模型的 `text` 仍是纯正文。
5. **记录起止行号**：解析时先把 CRLF 归一化为 LF，再用 bisect 把字符偏移映射为行号，避免 Windows 换行导致引用偏移。
6. **稳定 chunk ID**：`sha256(source_path | rel_path | ordinal | text)[:32]`；内容变化则 ID 变化，旧向量按 `document_id` 清理。
7. **过滤过短分块**：少于 10 字符的块不入库（多为空节或孤立符号）。

## 备选与取舍

| 方案 | 取舍 |
| --- | --- |
| **标题感知 + 长度上限（选择）** | 分块自带主题，引用可显示"文件 › 小节"；实现可解释、可测试。代价是分块长度不均匀，短节需合并、长节需二次切分。 |
| 固定窗口（如 800 字 / 120 重叠） | 实现最简单、长度稳定；但可能在句子或章节中间切断，引用读起来突兀，且丢失标题语义。 |
| 语义分块（句子嵌入找主题断点） | 理论上分块更自然；需要额外模型与阈值调参，收益在 1k～5k 规模不明显，属于过度工程。 |
| 父子块（小块检索、大块喂模型） | 能兼顾检索精度与上下文完整；实现与存储复杂度明显上升，留作阶段 2 评测后的可选优化。 |

## 后果

- 分块参数（600 / 100）目前是经验值，阶段 2 会用评测集对比 400/600/800 的 Recall@5 与引用准确率，并把结果写回本 ADR。
- 行号是"文件内行号"，不是页码；PDF 解析在阶段 5 接入时需要额外的页码映射。
- chunk ID 包含全文哈希：修改一个字就会重建该文件所有块。对 1k～5k 规模可接受，换来的是简单可靠的一致性。
- `tests/test_chunker.py` 覆盖标题路径、超长段落硬切、行号计算、CRLF、过短块过滤等行为。
