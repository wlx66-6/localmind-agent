# RAG 评测

## 为什么必须评测

RAG 系统很容易"看起来能用"：问几个问题，回答通顺，就以为成功了。但通顺不等于正确，引用也可能与原文无关。

没有评测集，调参只能靠感觉，改动检索策略后也无法判断是变好还是变坏。评测是把 RAG 从演示变成工程的关键一步。

## 评测集怎么构造

评测集是一组问题加标准答案，通常还包括答案来自哪个文档或片段。规模不必很大，30 到 50 题就能暴露主要问题。

题目要覆盖四类：

- 精确术语：例如某个错误码的含义，考察关键词召回。
- 语义改写：问题与原文用词不同，考察向量检索。
- 跨文档综合：答案需要多个片段拼接。
- 无答案：资料里确实没有，考察拒答。

无答案题最容易被忽略，但它直接决定系统会不会编造。

## 核心指标

Recall@5：正确片段是否出现在前 5 个检索结果中。它衡量检索能力，不涉及生成。

引用准确率：回答中的每个引用编号，是否真的支持对应陈述。人工抽查或规则校验都可以，关键是定义清楚。

拒答正确率：无答案题中，系统是否正确拒答；有答案题中，是否没有误拒。

首 token 延迟：从请求发出到第一个 token 的时间，影响交互体验。

## 指标之间的关系

Recall@5 高但引用准确率低，说明生成阶段没有正确使用上下文，或者提示词约束不够。

引用准确率高但 Recall@5 低，说明检索漏掉了部分资料，回答可能只覆盖问题的一部分。

拒答阈值调高会减少编造，但会增加误拒。两个错误都要统计，不能只看一边。

## 评测的运行方式

评测脚本应该可重复运行：固定语料、固定分块参数、固定模型版本。每次修改检索或提示词后重跑，记录指标变化。

结果写入版本库，和 ADR 一起保存。这样面试时可以展示"改了什么、指标怎么变"，而不是只说"效果不错"。
