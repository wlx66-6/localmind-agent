# 本地推理

## 为什么要在本地跑

本地推理意味着模型权重和输入数据都在本机，断网也能工作。对隐私敏感的场景，这是唯一能证明"数据没有出站"的方式。

代价是硬件限制。消费级笔记本的显存通常只有 8GB 左右，能运行的模型规模和上下文长度都受限。

## 量化

量化把模型权重从 16 位浮点压缩到更低位宽。常见的 Q4_K_M 是 4 位量化，在质量和体积之间比较平衡。

一个 4B 参数的模型，Q4 量化后大约占用 3GB 显存；7B 模型大约 4.5GB 到 5GB。显存还要留给 KV 缓存和推理框架本身。

量化会带来质量损失，但对"基于给定上下文组织答案"这类任务，4B 模型通常够用，因为事实来自检索片段，而不是模型记忆。

## Ollama 的用法

Ollama 提供兼容的 HTTP 接口，常用的有 /api/chat 和 /api/embed。模型加载后会在内存中保留一段时间，再次调用不需要重新加载。

聊天接口支持流式输出，可以测量首 token 延迟和每秒 token 数。嵌入接口支持批量输入，适合索引阶段。

一些模型默认开启思维链（thinking），会显著增加首 token 延迟和输出长度。应用层应显式关闭，除非确实需要推理过程。

## 显存共存的取舍

生成模型、嵌入模型和重排模型同时驻留，显存占用会接近上限。实测中三者合计可能达到 7.5GB 以上，只剩几百 MB 余量。

这时长上下文、更大的批处理或并发请求都可能导致显存不足。工程上要做降级：重排改 CPU、嵌入按需加载、或者换更小的生成模型。

降级顺序应该由延迟和质量的取舍决定，而不是简单地"哪个先报错就关哪个"。

## 性能基线

在 8GB 显存的笔记本上，4B 量化模型的首 token 延迟通常在几百毫秒，生成速度几十 token 每秒。嵌入模型单条十几毫秒，重排模型每个候选几毫秒。

这些数字会随驱动、量化和上下文长度变化，必须在目标机器上实测，不能直接引用别人的 benchmark。
